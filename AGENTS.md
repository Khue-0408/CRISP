# CRISP Research Engineering Contract

## Objective

CRISP is a research codebase supporting the journal development of a constrained boundary-posterior projection method for reliable dense prediction under cross-dataset shift.

The repository must preserve scientific correctness, controlled experimentation, reproducibility, and public-surface integrity.

## Source-of-truth hierarchy

1. The current full Neurocomputing manuscript defines scientific intent and experimental specification.
2. Actual local code, configuration, tests, and logs define implementation state.
3. Public GitHub and repository history provide historical baseline context only.
4. Engineering guidance is advisory and must not override scientific intent or observed implementation state.

When sources disagree, report the mismatch and do not silently reinterpret scientific meaning. Ask for a user decision when the missing choice changes scientific conclusions. Do not describe internal reconstruction history or infrastructure issues.

Scientifically relevant project instructions must be tracked. Ignored or machine-local AGENTS/context files must not become an authoritative source of project behavior.

## Core engineering principles

1. Think before coding.
2. Inspect the current branch, working tree, and all applicable `AGENTS.md` files before editing.
3. Prefer the smallest scientifically correct change.
4. Define observable success criteria before implementation.
5. Do not silently choose a scientific interpretation.
6. Separate verified fact, inference, assumption, and user decision.
7. Never claim a test, run, or result that was not actually executed.

## Scientific invariants

Never silently change the data split, dataset role, preprocessing, model definition, teacher behavior, boundary weighting, posterior target, projection family, solver semantics, projector semantics, training schedule, optimizer, metric definitions, threshold, checkpoint-selection rule, or evaluation protocol unless the task explicitly studies that factor.

Canonical CRISP behavior must remain unchanged unless a task explicitly defines a controlled ablation.

## Ablation discipline

A one-factor ablation must differ from its parent only in the declared scientific factor:

`Delta(actual resolved config) = Delta(declared ablation)`

Prefer config-controlled variants over duplicated implementation. Never infer scientific equivalence from filenames alone; inspect the resolved configuration and its runtime consumer.

## Evidence discipline

Never invent, interpolate, estimate, or hard-code experimental results. Distinguish configured, launched, completed, failed, verified, and reported states. A configuration file is not evidence that an experiment was run. Failed runs remain evidence and must not be silently erased.

## Result provenance

Future experiment records should be traceable to the experiment ID, parent or reference, hypothesis, resolved configuration, exact changed keys, seed, Git SHA, dataset and split identity, teacher and checkpoint identity, output path, metrics, and status.

Do not create or overwrite old experiment outputs silently.

## GPU / expensive jobs

Do not launch long training automatically. Use this default verification order:

1. static inspection;
2. targeted unit tests;
3. configuration validation;
4. lightweight smoke or integration tests.

Full training requires explicit user authorization.

## Testing

Run the narrowest meaningful checks first. Do not repeatedly rerun unchanged expensive tests without a reason. Scientific invariants deserve explicit tests, not only syntax or import tests.

## Public-surface integrity

Public repository artifacts must not contain private working history, including unavailable or lost infrastructure, deadline pressure, prompt or chat logs, AI-generation history, reconstruction or recovery narrative, private filesystem paths, credentials, or tokens.

Avoid wording equivalent to:

- replicated from the paper;
- reconstructed;
- recreated;
- recovered;
- reverse-engineered;
- generated by AI.

Do not invent download links or claim result reproduction without evidence.

## Completion report

For every non-trivial research-code change, report:

- initial branch and working-tree status;
- scientific objective and invariant;
- files and configuration keys changed;
- commands and tests actually executed;
- observed results and relevant diff summary;
- assumptions and remaining uncertainty;
- comparability impact;
- final Git status.

Do not commit or push unless explicitly authorized.
